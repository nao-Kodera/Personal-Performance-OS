## 0. この文書の役割

**本書はドメイン設計・DB設計より先に確定させる。**

理由: 分析に必要な値から逆算してデータモデルを決めるためである。この順序を逆にすると、「後から必要になった値が保存されていない」という取り返しのつかない事態が起きる。

たとえば実行率を算出したくなっても、実行しなかった記録（NonExecutionRecord）を保存していなければ、遡って作ることはできない。

本書は次を定める。

1. 分析の共通ルール（母集団・期間・最小サンプル数）
2. MVPで実装する6種の分析の完全な定義
3. 各分析が要求するデータ項目（→ ドメイン設計への入力）

---

## 1. 分析の目的と非目的

### 1.1 目的

各分析は、次の形の問いに答えるために存在する。

> 条件Xを満たすとき、成果指標Yはどうなるか。

条件Xは**作業前に確定している**もの（作業タイプ、時間帯、曜日、睡眠時間、場所）に限る。成果指標Yは**作業後に得られる**もの（集中度、成果度など）に限る。

この分離を守らない集計は作らない。たとえば「集中度が高いセッションの平均成果度」は、両方が結果側の指標であり、行動を変える判断に使えない。

### 1.2 非目的

| やらないこと | 理由 |
|---|---|
| 相関係数・p値・信頼区間の提示 | MVPのサンプル数（50件程度）では、統計的有意性を語れない。数値があると誤った確信を生む |
| 複数指標の合成スコア | どの要素が効いているか分からなくなる（[用語集 §6](02-glossary.md)） |
| 予測・推薦 | [PRD §7.3](01-product-requirements.md) |
| 結論文の自動生成 | 解釈は人間が行う（[UC-09](03-use-cases.md)） |
| 多変量分析・交互作用 | サンプル数が全く足りない。データ蓄積後に検討 |

## 2. 共通ルール

### 2.1 母集団

| ルール | 内容 |
|---|---|
| 対象 | `WorkSession.status = Completed` のセッションのみ |
| 除外1 | `status = InProgress`（未終了。結果が存在しない） |
| 除外2 | `status = Abandoned`（作業として成立していない） |
| 必須条件 | PerformanceResultが存在すること（Completedなら必ず存在する） |

**A-06（実行率）のみ母集団が異なる。** PlannedWorkを母集団とする。§4.6 を参照。

### 2.2 分析期間

| 項目 | 内容 |
|---|---|
| 判定基準 | `WorkSession.started_at` をJSTに変換した日付 |
| 既定 | 直近28日（本日を含む。本日 − 27日 〜 本日） |
| 選択肢 | 7日 / 28日 / 90日 / 全期間 |
| 境界 | 開始日の00:00:00(JST) 以上、終了日の翌日00:00:00(JST) 未満 |

深夜をまたぐセッション（22:00開始・翌01:00終了）は、**開始時刻の属する日**に集計する。終了日側には含めない（[用語集 §4](02-glossary.md)）。

### 2.3 最小サンプル数

| 項目 | 内容 |
|---|---|
| 閾値 | **5件** |
| 未満の場合 | 平均値を算出しない。「サンプル不足（n=3）」と表示する |
| グラフ | 該当区分のバーを描画しない。区分名と「サンプル不足」のみ表示 |

**この閾値を下げないこと。** 1〜2件の平均を根拠に行動を変えると、本プロダクトの目的である「再現条件の発見」に対して誤った結論を導く。数値を出さないことで判断を保留させる。

### 2.4 欠損の扱い

| 状況 | 扱い |
|---|---|
| DailyConditionが未記録の日のセッション | 日次条件を使う分析（A-05）から**除外**する。除外件数を画面に表示する |
| PlannedWorkに紐づかないセッション | 実行率（A-06）の分子・分母に含めない |
| PlannedWorkが実行もされず未実行記録もない | A-06 で「未処理」として分母には含め、分子には含めない |

**推測して補完しない。** 欠損は欠損として扱う（[PRD §8 原則4](01-product-requirements.md)）。

### 2.5 丸め

| 項目 | 内容 |
|---|---|
| 平均値 | 小数第2位で四捨五入（例: 3.67） |
| 割合 | 小数第1位で四捨五入し、パーセント表記（例: 68.4%） |
| 時間 | 分単位の整数。表示時は「93分」または「1時間33分」 |

計算はサーバー側で行い、丸めた値をレスポンスに含める。クライアントで再計算しない。

## 3. 集計軸の定義

### 3.1 軸の一覧

| 軸 | 導出元 | 区分数 | 用途 |
|---|---|---|---|
| WorkType | `WorkSession.work_type_id` | 6（初期値） | A-01, A-02 |
| TimeBand | `WorkSession.started_at`（JST）の時刻 | 4 | A-03 |
| DayOfWeek | `WorkSession.started_at`（JST）の曜日 | 7 | A-04 |
| SleepBand | 所属日の `DailyCondition.sleep_minutes` | 4 | A-05 |
| WorkLocation | `WorkContext.work_location` | 4 | （MVPでは未使用・データは保存する） |

### 3.2 区分数の設計制約

**区分数 × 5件（最小サンプル数）≦ 想定サンプル数** を満たすこと。

MVPの想定は4週間で50セッション（[PRD §9.1 S2](01-product-requirements.md)）である。

| 軸 | 区分数 | 必要最小件数 | 判定 |
|---|---|---|---|
| WorkType | 6 | 30 | 可（ただし偏りに注意） |
| TimeBand | 4 | 20 | 可 |
| DayOfWeek | 7 | 35 | 可（ただし偏りに注意） |
| SleepBand | 4 | 20 | 可（DailyConditionは28件が上限） |

**WorkTypeを7個以上に増やさないこと。** DayOfWeekは7区分で固定だが、平日に偏るため土日はサンプル不足になりやすい。これは想定内であり、「サンプル不足」表示で正しく扱う。

### 3.3 WorkLocationを分析に含めない理由

MVPの分析6種にWorkLocation別の集計を含めていないのは、**データを保存しないからではない**。保存はする。

理由は、初期段階で作業場所が偏る（自宅がほとんど）ことが想定され、区分間の比較が成立しないためである。データが蓄積し、場所が分散した段階で追加する。

**このように「保存するが集計しない」項目を明示的に持つことが重要である。** 逆（集計したいが保存していない）は取り返しがつかない。

## 4. 分析定義

### A-01 作業タイプ別の平均集中度

| 項目 | 内容 |
|---|---|
| **問い** | どの種類の作業で、自分は集中できるのか |
| **母集団** | 分析期間内の `status = Completed` のWorkSession |
| **集計軸** | WorkType |
| **指標** | `AVG(PerformanceResult.focus_level)` |
| **表示** | 横棒グラフ（0〜5スケール固定）+ 各区分の件数 |
| **並び順** | 平均値の降順。サンプル不足の区分は末尾 |

**算出手順**

```text
1. 分析期間内、status = Completed のWorkSessionを取得
2. work_type_id でグループ化
3. 各グループについて
     n     = セッション数
     avg   = AVG(focus_level)
   n < 5 の場合、avg は算出せず「サンプル不足」とする
4. avg の降順に並べる
```

**併記する情報**

- 各区分の件数 n
- 各区分の合計作業時間（分）
- 全体平均（母集団全体の平均集中度）— 各区分が全体と比べて高いか低いかを判断するため

**注意**

WorkTypeは `WorkSession.work_type_id` を使う。`TaskItem.work_type_id`（既定値）ではない。同じタスクでも回によって作業の性質が変わるため、実績値を使う（[用語集 WorkType](02-glossary.md)）。

---

### A-02 作業タイプ別の平均成果度

| 項目 | 内容 |
|---|---|
| **問い** | どの種類の作業で、自分は成果を出せるのか |
| **母集団** | A-01と同じ |
| **集計軸** | WorkType |
| **指標** | `AVG(PerformanceResult.output_level)` |
| **表示** | 横棒グラフ（0〜5スケール固定）+ 件数 |
| **並び順** | 平均値の降順 |

算出手順・併記情報はA-01と同じ（指標のみ異なる）。

**A-01とA-02を分けている理由**

集中度と成果度は一致しない。「集中できたが進まなかった」「散漫だったが成果は出た」は実際に起きる。合成せず別々に見ることで、そのズレ自体が発見になる。

画面上はA-01とA-02を**並べて表示する**こと。同じ軸の2指標を比較できるようにする。

---

### A-03 時間帯別の平均集中度

| 項目 | 内容 |
|---|---|
| **問い** | 1日のどの時間帯に集中できるのか |
| **母集団** | 分析期間内の `status = Completed` のWorkSession |
| **集計軸** | TimeBand（開始時刻 JST 基準・4区分） |
| **指標** | `AVG(PerformanceResult.focus_level)` |
| **表示** | 横棒グラフ + 件数 |
| **並び順** | **時系列順固定**（早朝 → 午前 → 午後 → 夜） |

**算出手順**

```text
1. 分析期間内、status = Completed のWorkSessionを取得
2. started_at を JST に変換し、時刻から TimeBand を決定
     05:00–08:59 → EarlyMorning
     09:00–11:59 → Morning
     12:00–16:59 → Afternoon
     17:00–04:59 → Evening
3. TimeBand でグループ化し、AVG(focus_level) と n を算出
4. n < 5 は「サンプル不足」
5. 時系列順に並べる
```

**並び順を平均値順にしない理由**

時間帯は順序尺度である。時系列で並べることで「午前がピークで午後に落ちる」といった形の傾向が読み取れる。平均値順に並べ替えると、この形が失われる。

**注意**

Evening（17:00–04:59）は日をまたぐ。判定は `17 <= hour || hour < 5` で行う。

---

### A-04 曜日別の平均成果度

| 項目 | 内容 |
|---|---|
| **問い** | 週のどの曜日に成果が出るのか |
| **母集団** | 分析期間内の `status = Completed` のWorkSession |
| **集計軸** | DayOfWeek（開始時刻 JST 基準・7区分） |
| **指標** | `AVG(PerformanceResult.output_level)` |
| **表示** | 横棒グラフ + 件数 |
| **並び順** | **月 → 日 固定** |

**算出手順**

```text
1. 分析期間内、status = Completed のWorkSessionを取得
2. started_at を JST に変換し、曜日を決定
3. 曜日でグループ化し、AVG(output_level) と n を算出
4. n < 5 は「サンプル不足」
5. 月曜〜日曜の順に並べる
```

**注意**

- 分析期間が7日の場合、各曜日は最大でも数件にしかならず、ほぼ全区分がサンプル不足になる。これは正しい挙動である
- 土日は稼働がなければ n=0 になる。「サンプル不足」ではなく「記録なし」と表示して区別する

---

### A-05 睡眠時間区分別の平均成果度

| 項目 | 内容 |
|---|---|
| **問い** | 睡眠時間は成果に影響するのか |
| **母集団** | 分析期間内の `status = Completed` かつ**所属日のDailyConditionが存在する**WorkSession |
| **集計軸** | SleepBand（4区分） |
| **指標** | `AVG(PerformanceResult.output_level)` |
| **表示** | 横棒グラフ + 件数 |
| **並び順** | **睡眠時間の昇順固定**（6時間未満 → 8時間以上） |

**算出手順**

```text
1. 分析期間内、status = Completed のWorkSessionを取得
2. 各セッションの所属日を算出（started_at を JST に変換した日付）
3. 所属日の DailyCondition を結合
     存在しない場合はそのセッションを除外し、除外件数を数える
4. sleep_minutes から SleepBand を決定
     < 360        → Under6
     360 – 419    → From6To7
     420 – 479    → From7To8
     >= 480       → Over8
5. SleepBand でグループ化し、AVG(output_level) と n を算出
6. n < 5 は「サンプル不足」
7. 睡眠時間の昇順に並べる
```

**必ず表示すること**

- 除外件数と理由: 「除外 12件（日次コンディション未記録）」
- 集計に使われた日数

**除外件数の表示が必要な理由**

DailyConditionの記録率が低いと、この分析は少数の記録した日だけを見ていることになる。しかも「記録する余裕があった日」というバイアスがかかる。除外件数を見せることで、結果の信頼度をユーザー自身が判断できる。

**注意**

- 1日のDailyConditionは、その日の**すべてのセッション**に適用される。1件のDailyConditionが複数セッションに紐づくのは正常
- したがって n はセッション数であり、日数ではない。両方を表示する

---

### A-06 開始予定に対する実行率

| 項目 | 内容 |
|---|---|
| **問い** | 立てた予定をどれだけ実行できているか。できない理由は何か |
| **母集団** | **PlannedWork**（他の分析と母集団が異なる） |
| **集計軸** | なし（全体）+ 未実行理由の内訳 |
| **指標** | 実行率、未実行率、未処理率 |
| **表示** | 数値（大） + 理由別の内訳（横棒または一覧） |

**算出手順**

```text
1. 分析期間内（target_date 基準）の PlannedWork を取得 = 分母 N
2. 各 PlannedWork を3状態に分類する
     実行済み  … WorkSession が紐づいている
                 （status を問わない。Abandoned でも「開始した」とみなす）
     未実行    … NonExecutionRecord が存在する
     未処理    … どちらも存在しない
3. 実行率   = 実行済み件数 / N
   未実行率 = 未実行件数 / N
   未処理率 = 未処理件数 / N
4. 未実行のものを reason でグループ化し、件数と割合を出す
```

**「実行済み」に Abandoned を含める理由**

A-06が問うのは「予定した作業に着手できたか」である。着手したが成立しなかったこと（Abandoned）は、着手すらしなかったこと（未実行）とは意味が違う。前者は実行率に含める。

ただし内訳として「うち中断終了 N 件」を併記し、区別できるようにする。

**未処理率を表示する理由**

未処理は「予定を立てたが、実行も未実行記録もしていない」状態である。これが多い場合、実行率そのものが信用できない。データ品質の指標として表示する。

**最小サンプル数の扱い**

A-06 は分母が PlannedWork であり、他の分析とは性質が異なる。ただし同じ閾値を適用する。

- N < 5 の場合、実行率を算出せず「サンプル不足（n=N）」とする
- 理由別内訳は N >= 5 の場合のみ表示する

**補助表示**

| 項目 | 内容 |
|---|---|
| 予定を立てた日数 | PlannedWorkが1件以上存在する日の数 |
| 1日あたり平均予定件数 | N / 予定を立てた日数 |
| 予定外セッション数 | `planned_work_id IS NULL` のCompletedセッション数 |

**予定外セッション数を表示する理由**

実行率が低くても、予定外の作業を多くこなしていれば、問題は「実行できないこと」ではなく「計画が実態に合っていないこと」である。この2つは対処が全く違う。

## 5. 補助指標

分析画面には表示しないが、履歴画面（S-08）で各セッションに表示する。

| 指標 | 算出式 | 表示 |
|---|---|---|
| 実作業時間 | `finished_at - started_at`（分） | 「93分」 |
| 疲労増加量 | `PerformanceResult.fatigue_after - PreWorkState.fatigue_level` | 「疲労 2→4 (+2)」 |
| 見込みとの差 | `PerformanceResult.focus_level - PreWorkState.expected_focus_level` | 「見込み3 → 実際4 (+1)」 |

**これらをDBに保存しない。** 導出可能な値であり、保存すると元データとの不整合が生じうる。都度算出する。

**「見込みとの差」の意味**

作業前に「集中できそう」と感じた度合いと、実際の集中度の差である。この差が常に負なら、自分の状態認識が楽観的すぎることを意味する。MVPでは表示のみ行い、集計はしない。

## 6. データモデルへの要求

**本セクションが、本書からドメイン設計・DB設計への引き渡し事項である。**

以下の項目が保存されていなければ、対応する分析は実装できない。

| 必要な項目 | 保持する概念 | これがないと不可能になる分析 |
|---|---|---|
| セッションの作業タイプ（実績値） | WorkSession | A-01, A-02 |
| セッションの開始時刻（正確な時刻） | WorkSession | A-03, A-04, 期間絞り込み |
| セッションの終了時刻 | WorkSession | 実作業時間 |
| セッションの状態（3値） | WorkSession | 母集団の絞り込み |
| 集中度 | PerformanceResult | A-01, A-03 |
| 成果度 | PerformanceResult | A-02, A-04, A-05 |
| 正確性・満足度 | PerformanceResult | （MVPでは未集計。履歴表示のみ） |
| 作業前疲労度 | PreWorkState | 疲労増加量 |
| 終了時疲労度 | PerformanceResult | 疲労増加量 |
| 見込み集中度 | PreWorkState | 見込みとの差 |
| 睡眠時間（分） | DailyCondition | A-05 |
| DailyConditionの対象日（JST） | DailyCondition | A-05 の結合キー |
| 予定の存在 | PlannedWork | **A-06（後から作成不可）** |
| 予定と実績の紐づけ | WorkSession.planned_work_id | **A-06（後から作成不可）** |
| 未実行の事実と理由 | NonExecutionRecord | **A-06（後から作成不可）** |
| 作業場所 | WorkContext | 将来の場所別分析 |
| 会議件数・割り込み予想 | WorkContext | 将来の環境別分析 |
| 中断回数 | WorkSession | 将来の中断影響分析 |

**太字の3項目は、記録し損ねると遡って復元できない。** 実装の優先度を下げないこと。

## 7. パフォーマンス方針

| 項目 | 内容 |
|---|---|
| データ規模の想定 | 3年で約2,000セッション、1,100日次記録 |
| 集計方式 | 都度SQL集計。事前集計テーブル・キャッシュは持たない |
| 必要なインデックス | `work_sessions(started_at)`, `work_sessions(status)`, `daily_conditions(target_date)`, `planned_works(target_date)` |

この規模では都度集計で十分に速い。事前集計を入れると、記録の訂正時に再計算が必要になり複雑さが増す。導入しない。

| 会議件数別の平均成果度 | なし（保存済み） | 3ヶ月後 |
| 中断回数と集中度の関係 | なし（保存済み） | 3ヶ月後 |
| 疲労増加の作業タイプ別比較 | なし（保存済み） | 3ヶ月後 |
| 連続作業時間と成果度の関係 | なし（保存済み） | 3ヶ月後 |
| 前日の睡眠と翌日の成果 | なし（保存済み） | 3ヶ月後 |
| 見込み集中度の予測精度 | なし（保存済み） | 3ヶ月後 |
