## 0. このプロダクトの前提（最重要）

> **タスクを管理することが目的ではない。**
> **自分の状態・環境・行動・成果を観測し、高いパフォーマンスが出る条件を発見して再現することが目的である。**

この一文が、本プロダクトのすべての設計判断の上位にある。
仕様追加・設計変更を検討する際は、必ずこの目的に照らして判断すること。

以下は本プロダクトでは**目的ではない**。

- タスクを漏れなく管理すること
- ToDoを消化して達成感を得ること
- プロジェクトの進捗を可視化すること
- 他人と進捗を共有すること

タスクは「観測の単位」として存在する。タスク管理機能は、観測対象である作業を識別するために最小限だけ持つ。

## 1. 背景

個人の作業パフォーマンスは日によって大きく変動する。同じ種類の作業でも、集中できる日とまったく進まない日がある。

しかし多くの場合、その変動は「今日は調子が悪かった」という主観的な記憶で処理され、原因が特定されないまま繰り返される。

一方で、変動には再現性のある条件が存在する可能性が高い。たとえば以下のような条件である。

- 睡眠時間が6時間を下回った日は、思考を要する作業の成果が落ちる
- 午前中は設計作業の集中度が高いが、午後は同じ作業でも落ちる
- 会議が2件以上入った日は、まとまった実装作業が成立しない
- 自宅よりカフェの方が、ドキュメント作成の成果度が高い

これらは体感としては存在するが、記録がないため確信が持てず、行動の決定に使えない。

既存の生産性ツールはタスクの「完了/未完了」を記録するが、**そのタスクをどのような状態・環境で実行し、結果としてどうだったか**を記録しない。したがって条件の発見に使えない。

## 2. 解決したい問題

| # | 問題 | 現状 |
|---|---|---|
| P1 | 自分が高いパフォーマンスを出せる条件を把握していない | 体感はあるが根拠がなく、行動を変える判断ができない |
| P2 | 調子の良し悪しの原因が事後に特定できない | 記録が残らないため、良かった日の再現ができない |
| P3 | 作業の種類と時間帯・状態のミスマッチに気づけない | 集中を要する作業を、集中できない条件下で実行し続けてしまう |
| P4 | 「やる予定だったができなかった」が記録に残らない | 実行率が測れず、計画の妥当性を検証できない |
| P5 | 記録を試みても続かない | 記録コストが高いツールしか存在しない |

**P4は特に重要である。** 実行しなかった記録を保存しない限り、「開始率」「計画の妥当性」は永久に算出できない。多くのツールはこれを捨てている。

**P5も設計制約として扱う。** 記録が続かなければデータが貯まらず、分析は成立しない。記録コストの最小化は機能要件と同等の優先度を持つ。

## 3. プロダクトの目的

本プロダクトは、以下のサイクルを回すための個人用の観測・分析基盤である。

```text
1. 観測  … 状態・環境・行動・成果を、作業単位で記録する
2. 発見  … 記録を集計し、パフォーマンスと相関する条件を見つける
3. 再現  … 発見した条件を満たすように、次の行動を選択する
4. 検証  … 再現できたかを再び観測する
```

MVPが責任を持つのは **1（観測）と 2（発見）** である。
3と4は人間が行う。アプリが行動を推薦することはMVPでは行わない。

## 4. 観測対象

本プロダクトが観測するのは、以下の4層である。この4層の分離は、後続のドメイン設計・DB設計でも維持する。

| 層 | 内容 | 記録タイミング | 性質 |
|---|---|---|---|
| **状態** | 睡眠時間、体調、気分、疲労度、ストレス | 1日1回 + 作業開始前 | 作業前に確定している事実 |
| **環境** | 作業場所、時間帯、曜日、会議の量、割り込みの有無 | 作業開始前 | 自分の外部にある条件 |
| **行動** | 作業タイプ、開始時刻、終了時刻、中断回数 | 作業中〜終了時 | 実際に起きたこと |
| **成果** | 集中度、成果度、正確性、満足度、終了時疲労度 | 作業終了直後 | 結果として得られたもの |

### 4.1 分離の理由

**「開始前の状態」「作業中の事実」「作業後の結果」は、必ず別の記録として保持する。**

これらを1つのレコードに詰めると、以下ができなくなる。

- 「開始前の状態」を説明変数、「作業後の結果」を目的変数として扱う分析
- 作業を開始したが結果を記録しなかったケースの表現
- 作業を開始しなかったケース（結果が存在しない）の表現

### 4.2 記録の順序

```text
[1日の開始] DailyCondition を記録
              ↓
[作業の直前] PreWorkState を記録  ← 状態・環境（結果を知らない時点で確定する）
              ↓
[作業の開始] WorkSession を開始
              ↓
[作業の終了] WorkSession を終了 + PerformanceResult を記録  ← 成果
```

PreWorkStateを「結果を知らない時点で」記録することには意味がある。事後に記録すると、結果に引きずられた評価（「うまくいったから体調も良かったことにする」）が混入し、分析が成立しなくなる。

## 5. 成果の定義

「成果」を何とみなすかを固定する。MVPでは以下の5指標を、作業終了直後に本人が5段階で評価する。

| 指標 | 問い | 尺度 |
|---|---|---|
| 集中度 | どれだけ作業に没入できたか | 1〜5 |
| 成果度 | 意図した進捗をどれだけ得られたか | 1〜5 |
| 正確性 | 手戻りの少なさ・質の高さ | 1〜5 |
| 満足度 | その作業時間に納得できるか | 1〜5 |
| 終了時疲労度 | 終了時点の疲労 | 1〜5 |

### 5.1 主観評価を一次データとする理由

客観指標（コード行数、完了タスク数など）は、作業の種類によって意味が変わり、横断比較ができない。また計測に外部連携が必要でMVPの範囲を超える。

一方、本人の主観評価は次の条件を満たす限り、条件発見の目的には十分な精度を持つ。

- 評価尺度が全期間で固定されている
- 評価が作業終了直後に行われる（記憶の劣化前）
- 評価者が1人である（評価者間のばらつきが存在しない）

**したがって、評価尺度の定義は後から変更しない。** 変更する場合は、変更時点以降のデータを別系列として扱う必要がある。

### 5.2 補助指標

以下は主観評価ではなく事実として記録し、成果指標の解釈に用いる。

- 実作業時間（終了時刻 − 開始時刻）
- 中断回数
- 疲労増加量（終了時疲労度 − 開始前疲労度）

## 6. 対象ユーザー

**単一ユーザー（本プロダクトの開発者本人）。**

- 知識労働者であり、作業内容が日によって異なる
- 自分の記録を自分で分析する意思がある
- 記録の入力を毎日行う

MVPでは複数ユーザー・認証・データ共有を扱わない。ただし、将来的な複数ユーザー化を不可能にする設計（ユーザー識別子を持たないなど）は避ける。

## 7. MVPの範囲

### 7.1 含むもの

| # | 機能 | 目的 |
|---|---|---|
| F1 | タスクの登録・一覧・更新 | 観測単位の識別 |
| F2 | 作業タイプ（WorkType）の管理 | 作業の分類軸 |
| F3 | 1日のコンディション記録 | 状態層の観測 |
| F4 | 作業開始前状態の記録 | 状態層・環境層の観測 |
| F5 | 作業セッションの開始・終了（中断終了を含む） | 行動層の観測 |
| F6 | 作業成果の評価入力 | 成果層の観測 |
| F7 | 実行しなかった記録（NonExecutionRecord） | 実行率の算出 |
| F8 | 記録履歴の閲覧 | 観測結果の確認 |
| F9 | 基本分析6種の表示 | 条件の発見 |

### 7.2 分析（F9）の初期6種

分析仕様は別ドキュメント（分析仕様書）で定義するが、MVPで表示する分析は以下に固定する。

1. 作業タイプ別の平均集中度
2. 作業タイプ別の平均成果度
3. 時間帯別の平均集中度
4. 曜日別の平均成果度
5. 睡眠時間帯別の平均成果度
6. 開始予定に対する実行率

**この6種を先に固定した理由：** 分析を後から決めると、必要なデータが保存されていない事態が起きる。データモデルはこの6種から逆算して設計する。

### 7.3 含まないもの

以下はMVPに含めない。実装しない理由を明記する。

| 除外項目 | 理由 |
|---|---|
| 認証・ユーザー管理 | 単一ユーザー。観測と分析の検証に不要 |
| AIによる分析・推薦 | データが貯まる前に推薦しても根拠がない。まず観測を成立させる |
| 通知・リマインダー | 記録の習慣化はまず手動で検証する |
| モバイルアプリ | Web（レスポンシブ）で足りるかを先に確認する |
| 外部連携（カレンダー、ウェアラブル、Git） | 自動取得は有用だが、まず何を観測すべきかを確定させる |
| タスクの階層構造・依存関係・ガント | タスク管理アプリ化を招く。観測に不要 |
| 繰り返しタスク | 同上 |
| 統計的検定・相関係数の提示 | サンプル数が不足する初期に誤った確信を与える。平均値の比較にとどめる |
| データのエクスポート/インポート | 分析が有効と確認できてから |
| チーム機能・共有 | 対象外 |

**「タスクの階層構造」「繰り返しタスク」「ガント」を明示的に除外していることに注意すること。** これらは一般的なタスク管理アプリの標準機能だが、本プロダクトの目的には寄与せず、実装するとプロダクトの性格が変わる。

## 8. 設計原則

実装判断で迷った場合の優先順位。

1. **観測の完全性 > 入力の快適さ > 見た目**
   ただし、記録が続かないなら観測は成立しない。以下の記録コスト上限を守る。
   - 作業開始前の入力: **30秒以内**
   - 作業終了時の入力: **60秒以内**
   - 1日のコンディション入力: **30秒以内**
   これを超える入力項目は、追加せず既存項目の見直しで対応する。

2. **記録しなかったことも記録する**
   実行しなかった、評価しなかった、という状態を表現できるモデルにする。NULLで済ませず、意味のある状態として扱う。

3. **事後編集を許すが、記録時刻は保持する**
   評価を後から書き換えた場合、「いつ記録されたか」は残す。事後評価は分析時に区別できるようにする。

4. **推測して埋めない**
   未入力の項目をシステムが補完しない。欠損は欠損として扱う。

5. **分析仕様にない集計を先に作らない**
   実装可能だからという理由で分析軸を増やさない。

## 9. 成功条件

MVPが成功したかどうかを、以下で判定する。

### 9.1 定量条件

| # | 条件 | 期限 |
|---|---|---|
| S1 | 記録が28日間継続する（欠測日が4日以内） | 運用開始から4週間後 |
| S2 | WorkSessionが50件以上蓄積される | 運用開始から4週間後 |
| S3 | 作業開始前の入力が平均30秒以内で完了する | 運用開始から2週間後 |
| S4 | 分析6種のすべてが、サンプル数不足なく表示される | 運用開始から4週間後 |

### 9.2 定性条件

| # | 条件 |
|---|---|
| S5 | 分析結果から、パフォーマンスに影響する条件を**3つ以上**言語化できる |
| S6 | S5の条件のうち1つ以上について、実際に行動を変える判断ができる |
| S7 | 体感と分析結果が食い違う点が1つ以上見つかる（記録する価値の証明） |

### 9.3 失敗と判定する条件

- 記録が2週間以内に途絶える → 記録コストの設計が誤っている
- 分析結果がすべて体感どおりで、新しい発見がゼロ → 観測対象の選定が誤っている

失敗した場合、機能追加ではなく**観測対象または記録フローの見直し**を行う。

## 10. 基本用語

正式な用語集は別ドキュメントで定義する。ここでは本書の理解に必要な最小限を示す。

| 用語 | 定義 |
|---|---|
| **TaskItem** | 観測対象となる作業の単位。「何をするか」を表す |
| **WorkType** | 作業の分類（実装、設計、ドキュメント、調査、会議 など）。分析の主要な軸 |
| **DailyCondition** | 1日1件記録される、その日の身体・精神の状態（睡眠時間など） |
| **PreWorkState** | 作業開始直前に記録される、本人の状態と作業環境。**結果を知らない時点で確定する** |
| **WorkSession** | 実際に行われた1回の作業。開始時刻と終了時刻を持つ |
| **PerformanceResult** | WorkSessionに対する成果の評価。作業終了直後に記録される |
| **WorkContext** | 作業が行われた環境情報（場所、会議量、割り込みなど） |
| **PlannedWork** | 「この作業をこの時間にやる」という事前の予定 |
| **NonExecutionRecord** | PlannedWorkが実行されなかったという記録。実行率の分母を成立させる |

## 11. 想定する利用シーン

```text
朝
  DailyCondition を記録する（睡眠時間、体調、気分）
  今日やる PlannedWork を登録する

作業前
  PreWorkState を記録する（今の疲労、場所、これからやるWorkType）
  WorkSession を開始する

作業後
  WorkSession を終了する
  PerformanceResult を記録する（集中度、成果度、正確性、満足度、疲労）

やらなかったとき
  NonExecutionRecord を記録する（理由）

週末
  分析画面を見る
  条件を言語化する
```

## 12. タスク管理アプリとの違い

実装中にこの違いが失われていないかを確認するための基準。

| 観点 | 一般的なタスク管理アプリ | 本プロダクト |
|---|---|---|
| 中心となるデータ | タスク | 作業セッションと、その前後の状態 |
| 完了の意味 | ゴール | 観測の1件 |
| 未実行の扱い | 未完了として残る（負債） | 記録すべき事実（分析対象） |
| 記録するタイミング | タスク作成時と完了時 | 作業前・作業中・作業後の3回 |
| 主要な画面 | タスク一覧 | 記録フローと分析 |
| 成功の定義 | タスクが消化されること | 高パフォーマンスの条件が発見されること |
| ユーザーが得るもの | 進捗の可視化 | 自分の再現条件の理解 |

**判定基準：** 実装した機能が「タスクを消化しやすくするため」のものであれば、それはスコープ外である。「作業の条件と結果を観測するため」のものであればスコープ内である。

## 13. 前提と未確定事項

本書の初版時点で未確定だった事項。後続の設計書ですべて確定済み。

| # | 項目 | 確定値 | 確定した文書 |
|---|---|---|---|
| A1 | 評価尺度の段階数 | 5段階（1〜5）。全期間で固定 | [用語集 §2](02-glossary.md) |
| A2 | WorkTypeの初期値 | 実装 / 設計 / ドキュメント / 調査 / 会議 / その他（6種）。**7種以上に増やさない** | [用語集 §1](02-glossary.md) / [分析仕様 §3.2](04-analytics-spec.md) |
| A3 | 睡眠時間の記録粒度 | 15分単位。内部は分（integer）で保持 | [用語集 §3.3](02-glossary.md) |
| A4 | 作業場所の選択肢 | 自宅 / オフィス / カフェ / その他（その他のみ補足テキスト可） | [用語集 §3.1](02-glossary.md) |
| A5 | 時間帯の区切り | **6区分 → 4区分に変更**（早朝05-08 / 午前09-11 / 午後12-16 / 夜17-04） | [用語集 §3.2](02-glossary.md) |
| A6 | 睡眠時間帯の区切り | **5区分 → 4区分に変更**（〜6h / 6-7h / 7-8h / 8h〜） | [用語集 §3.3](02-glossary.md) |
| A7 | 中断回数の記録方法 | 作業中画面でカウントし、終了時にまとめて送信・訂正可 | [UC-05](03-use-cases.md) |
| A8 | 1セッションの最大長 | 上限なし。8時間超・1分未満は警告のみ（保存は妨げない） | [UC-05](03-use-cases.md) |

**A5・A6を仮置きから減らした理由**

MVPの想定サンプル数は4週間で50セッション（§9.1 S2）である。最小サンプル数を5件とすると（[分析仕様 §2.3](04-analytics-spec.md)）、6区分では1区分あたり平均8件となり、偏りを考えると多くの区分が「サンプル不足」で表示されない。4区分なら平均12件となり、成功条件S4を満たす見込みが立つ。

データが蓄積した段階で細分化を検討する。**区分は後から細かくできるが、記録していない項目は後から作れない。**

### 13.1 本書の初版から変更した事項

| # | 変更 | 理由 |
|---|---|---|
| C1 | WorkSessionに `Abandoned`（中断終了）状態を追加 | 開始したが成立しなかったセッションに終端状態がないと、InProgressのまま残り「同時1件」制約で次の作業を開始できなくなる。§7.1 F5 に反映済み |
| C2 | A5・A6 の区分数を削減 | 上記のとおり |

## 14. 技術方針（概要）

詳細は技術設計書で定義する。本書では方針のみ記す。

```text
フロントエンド   React + TypeScript
バックエンド     ASP.NET Core Web API + Entity Framework Core
データベース     PostgreSQL
開発環境         Docker Compose
テスト           xUnit / React Testing Library
```

バックエンド構成:

```text
PerformanceOs.Api
PerformanceOs.Application
PerformanceOs.Domain
PerformanceOs.Infrastructure
```

- 日時はDBにUTCで保存し、表示時にJST（Asia/Tokyo）へ変換する
- 初期段階でCQRS・MediatR等は導入しない。必要になった時点で検討する
