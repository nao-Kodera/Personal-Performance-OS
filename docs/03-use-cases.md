## 0. この文書の役割

ユーザーがアプリで何をするかを定義する。ここに書かれていない操作は実装しない。

**記録コストの制約を守ること。** 各ユースケースには目標入力時間を記載している。これは[PRD §8 原則1](01-product-requirements.md)に基づく設計制約であり、達成できない場合は入力項目を減らす。

## 3. ユースケース詳細

### UC-01 タスクを登録する

| 項目 | 内容 |
|---|---|
| **目的** | 観測単位となるTaskItemを作る |
| **アクター** | ユーザー |
| **事前条件** | WorkTypeが1件以上存在する |
| **目標入力時間** | 15秒 |

**操作手順**

1. S-02（タスク）を開く
2. タイトルを入力する（必須）
3. 既定のWorkTypeを選択する（必須）
4. メモを入力する（任意）
5. 「登録」を押す

**正常終了**

- TaskItemが保存される
- 一覧の先頭に表示される

**例外**

| 条件 | 挙動 |
|---|---|
| タイトルが空 | 「登録」を無効化し、入力を促す |
| タイトルが200文字超 | エラー表示、保存しない |
| 同名のTaskItemが既に存在 | **保存する**（重複を禁止しない）。同じ名前の作業を別の機会に行うことは正常 |

**保存されるデータ**

```text
TaskItem
  title            必須
  work_type_id     必須（既定のWorkType）
  note             任意
  is_archived      false
  created_at       システム
  updated_at       システム
```

**補足**

- TaskItemに「完了」操作はない。使わなくなったらアーカイブする。
- アーカイブしたTaskItemは、S-04の選択肢に表示されない。ただし過去のWorkSessionからは参照され続ける（削除しない）。

### UC-02 今日のコンディションを記録する

| 項目 | 内容 |
|---|---|
| **目的** | その日の土台となる状態を観測する |
| **アクター** | ユーザー |
| **事前条件** | なし |
| **目標入力時間** | 30秒 |

**操作手順**

1. S-01（ホーム）で「今日のコンディションを記録」を押す（未記録の場合のみ表示）
2. S-03 が開く
3. 睡眠時間を入力する（必須・15分単位）
4. 体調を選ぶ（必須・1〜5）
5. 気分を選ぶ（必須・1〜5）
6. ストレスを選ぶ（必須・1〜5）
7. メモを入力する（任意）
8. 「記録」を押す

**正常終了**

- DailyConditionが保存される
- S-01 に戻り、記録済みの状態が表示される

**例外**

| 条件 | 挙動 |
|---|---|
| 同じ日のDailyConditionが既に存在 | 新規作成ではなく**更新**する。S-03を開いた時点で既存値を表示する |
| 睡眠時間が0分または24時間超 | エラー表示、保存しない |
| 睡眠時間が15分の倍数でない | 入力UIで15分刻みしか選べないようにする（バリデーションで弾かない） |

**保存されるデータ**

```text
DailyCondition
  target_date          必須（JST基準の日付）
  sleep_minutes        必須（15の倍数、1〜1440）
  physical_condition   必須（1〜5）
  mood_level           必須（1〜5）
  stress_level         必須（1〜5）
  note                 任意
  recorded_at          システム（初回記録時刻）
  updated_at           システム
```

**補足**

- 対象日は**当日固定**とする。過去日の遡り入力はMVPでは許可しない。事後の記憶に基づく記録は精度が低く、[PRD §8 原則3](01-product-requirements.md)の趣旨に反するため。
- 未記録の日があってよい。強制しない。

---

### UC-03 作業予定を登録する

| 項目 | 内容 |
|---|---|
| **目的** | 実行率の分母を作る |
| **アクター** | ユーザー |
| **事前条件** | TaskItemが1件以上存在する |
| **目標入力時間** | 30秒（1日分まとめて） |

**操作手順**

1. S-01（ホーム）の「今日の予定」セクションで「予定を追加」を押す
2. TaskItemを選ぶ（必須）
3. WorkTypeを選ぶ（既定値はTaskItemのWorkTypeを自動選択。変更可）
4. 予定時間帯を選ぶ（任意・TimeBandの4区分）
5. 予定所要時間を入力する（任意・15分単位）
6. 「追加」を押す
7. 必要な数だけ2〜6を繰り返す

**正常終了**

- PlannedWorkが保存される
- S-01 の「今日の予定」に追加される

**例外**

| 条件 | 挙動 |
|---|---|
| TaskItem未選択 | 「追加」を無効化 |
| 同じTaskItem・同じ日の予定が既に存在 | **保存する**（同じ作業を1日に複数回予定することは正常） |

**保存されるデータ**

```text
PlannedWork
  target_date          必須（JST基準の日付）
  task_item_id         必須
  work_type_id         必須
  planned_time_band    任意
  planned_minutes      任意（15の倍数）
  created_at           システム
```

**補足**

- 予定を立てずに作業を開始してよい（UC-04参照）。予定は実行率の分析にのみ使う。
- 対象日は当日固定。翌日以降の予定登録はMVPでは扱わない。

### UC-04 作業開始前の状態を記録して作業を開始する

**本プロダクトで最も重要なユースケース。**

| 項目 | 内容 |
|---|---|
| **目的** | 結果を知らない時点での状態・環境を確定させ、作業を開始する |
| **アクター** | ユーザー |
| **事前条件** | TaskItemが1件以上存在する／InProgressのWorkSessionが存在しない |
| **目標入力時間** | 30秒 |

**操作手順**

1. S-01（ホーム）で「作業を開始」を押す。予定から開始する場合は、予定行の「開始」を押す
2. S-04 が開く
3. TaskItemを選ぶ（予定から開始した場合は選択済み）
4. WorkTypeを確認・変更する（既定値は自動選択済み）
5. **作業前状態**を入力する
   - 疲労度（必須・1〜5）
   - 見込み集中度（必須・1〜5）
   - 気分（必須・1〜5）
6. **作業環境**を入力する
   - 作業場所（必須・4区分）
   - 場所の補足（`その他` を選んだ場合のみ・任意）
   - 今日の会議件数（必須・0以上の整数。既定値0）
   - 割り込みが予想されるか（必須・はい/いいえ。既定値いいえ）
7. 「開始」を押す

**正常終了**

- WorkSession（status = InProgress）、PreWorkState、WorkContextが**同一トランザクションで**保存される
- 予定から開始した場合、PlannedWorkとWorkSessionが紐づく
- S-05（作業中）に遷移する

**例外**

| 条件 | 挙動 |
|---|---|
| InProgressのWorkSessionが既に存在 | S-04を開かせない。S-01 で「作業中」を表示し、S-05 への導線のみ出す |
| 必須項目が未入力 | 「開始」を無効化 |
| 当日のDailyConditionが未記録 | **警告を出すが、開始を妨げない**。「日次コンディションが未記録です。睡眠に関する分析に反映されません」と表示し、S-03への導線を出す |
| 選択したTaskItemがアーカイブ済み | 選択肢に表示しない |

**保存されるデータ**

```text
WorkSession
  task_item_id       必須
  work_type_id       必須（実績値）
  planned_work_id    任意（予定から開始した場合）
  started_at         システム（UTC）
  finished_at        NULL
  status             InProgress
  interruption_count 0
  created_at         システム

PreWorkState
  work_session_id       必須
  fatigue_level         必須（1〜5）
  expected_focus_level  必須（1〜5）
  mood_level            必須（1〜5）
  recorded_at           システム

WorkContext
  work_session_id     必須
  work_location       必須（Home/Office/Cafe/Other）
  location_note       任意（work_location = Other のときのみ）
  meeting_count       必須（0以上）
  interruption_expected 必須（bool）
  recorded_at         システム
```

**補足**

- **入力項目を増やさないこと。** 現在7項目で30秒に収まる想定。項目を足す場合は、既存項目を削るか、分析仕様上の必要性を証明すること。
- 既定値を積極的に使う（会議件数0、割り込みなし、WorkTypeはタスクから継承）。これが30秒制約を満たす主要な手段である。
- 「同時にInProgressは1件まで」の制約は、観測単位を成立させるためのもの（[用語集 WorkSession](02-glossary.md)）。並行作業を記録しても、どちらの成果か分離できない。

### UC-05 作業を終了して成果を評価する

| 項目 | 内容 |
|---|---|
| **目的** | 作業の事実を確定し、成果を評価する |
| **アクター** | ユーザー |
| **事前条件** | InProgressのWorkSessionが存在する |
| **目標入力時間** | 60秒 |

**操作手順**

1. S-05（作業中）で「終了」を押す
2. S-06 が開く。経過時間と対象タスクが表示される
3. 中断回数を確認・修正する（S-05でカウントした値が初期表示。0以上の整数）
4. 成果を入力する
   - 集中度（必須・1〜5）
   - 成果度（必須・1〜5）
   - 正確性（必須・1〜5）
   - 満足度（必須・1〜5）
   - 終了時疲労度（必須・1〜5）
5. メモを入力する（任意）
6. 「記録して終了」を押す

**正常終了**

- WorkSessionが `status = Completed`、`finished_at` 設定済みで更新される
- PerformanceResultが保存される
- 作業前疲労度と終了時疲労度の差（疲労増加量）が画面に表示される
- S-01 に戻る

**例外**

| 条件 | 挙動 |
|---|---|
| 5指標のいずれかが未入力 | 「記録して終了」を無効化。**スキップ導線は設けない** |
| 経過時間が8時間を超えている | 警告を表示する。「8時間を超えています。記録し忘れの可能性があります」。ただし保存は妨げない |
| 経過時間が1分未満 | 警告を表示する。「1分未満です。中断終了として記録しますか?」とUC-06への導線を出す。ただし通常終了も可能 |
| 画面を離脱した | WorkSessionはInProgressのまま残る。次回S-01で「作業中」として表示され、S-06へ復帰できる |

**保存されるデータ**

```text
WorkSession（更新）
  finished_at         システム（UTC）
  status              Completed
  interruption_count  必須（0以上）
  updated_at          システム

PerformanceResult
  work_session_id      必須
  focus_level          必須（1〜5）
  output_level         必須（1〜5）
  accuracy_level       必須（1〜5）
  satisfaction_level   必須（1〜5）
  fatigue_after        必須（1〜5）
  note                 任意
  recorded_at          システム（初回記録時刻）
  updated_at           システム
```

**補足**

- `finished_at` はサーバー側の現在時刻を使う。ユーザーによる時刻の手入力は許可しない（記録の信頼性を保つため）。
- 疲労増加量はDBに保存しない。`fatigue_after - PreWorkState.fatigue_level` で都度算出する（[分析仕様 §5](04-analytics-spec.md)）。

### UC-06 作業を中断終了する

| 項目 | 内容 |
|---|---|
| **目的** | 作業として成立しなかったセッションを、分析対象外として確定させる |
| **アクター** | ユーザー |
| **事前条件** | InProgressのWorkSessionが存在する |
| **目標入力時間** | 15秒 |

**操作手順**

1. S-05（作業中）で「中断終了」を押す
2. 確認ダイアログが出る。「成果は記録されず、分析の対象外になります」
3. 理由メモを入力する（任意）
4. 「中断終了する」を押す

**正常終了**

- WorkSessionが `status = Abandoned`、`finished_at` 設定済みで更新される
- PerformanceResultは作成されない
- S-01 に戻る

**例外**

| 条件 | 挙動 |
|---|---|
| 既に終了済み | エラー。「このセッションは既に終了しています」 |

**保存されるデータ**

```text
WorkSession（更新）
  finished_at       システム（UTC）
  status            Abandoned
  abandon_note      任意
  updated_at        システム
```

**補足**

- Abandonedは分析の母集団から除外する（[分析仕様 §2](04-analytics-spec.md)）が、履歴には表示する。
- 「開始したが作業にならなかった」という事実自体が情報である。削除しない（[PRD §8 原則2](01-product-requirements.md)）。
- UC-07（未実行記録）との違い: UC-06は**開始した**が成立しなかった。UC-07は**開始しなかった**。

### UC-07 作業しなかったことを記録する

| 項目 | 内容 |
|---|---|
| **目的** | 実行率の算出と、計画の妥当性検証 |
| **アクター** | ユーザー |
| **事前条件** | 当日のPlannedWorkのうち、未実行のものが存在する |
| **目標入力時間** | 15秒 |

**操作手順**

1. S-01（ホーム）の「今日の予定」で、未実行の予定行の「やらなかった」を押す
2. S-07（またはモーダル）が開く
3. 理由区分を選ぶ（必須・6区分）
4. 詳細メモを入力する（任意）
5. 「記録」を押す

**正常終了**

- NonExecutionRecordが保存される
- 該当のPlannedWorkが「未実行（理由）」として表示される

**例外**

| 条件 | 挙動 |
|---|---|
| 該当PlannedWorkに既にWorkSessionが紐づいている | 「やらなかった」ボタンを表示しない |
| 既にNonExecutionRecordが存在 | 新規作成ではなく**更新**する |

**保存されるデータ**

```text
NonExecutionRecord
  planned_work_id   必須
  reason            必須（NoTime/Interrupted/PoorCondition/Deprioritized/Overplanned/Other）
  note              任意
  recorded_at       システム
  updated_at        システム
```

**補足**

- **このユースケースを省略しないこと。** 未実行記録がなければ、実行率（分析A-06）は算出できない。後から遡って作れない唯一のデータである。
- 記録を促す導線として、S-01 に「未処理の予定が N 件あります」を表示する。ただし強制はしない。

### UC-08 過去の記録を見る

| 項目 | 内容 |
|---|---|
| **目的** | 記録された事実を確認し、必要なら訂正する |
| **アクター** | ユーザー |
| **事前条件** | なし |

**操作手順**

1. S-08（履歴）を開く
2. 日付単位でグルーピングされたWorkSessionの一覧が表示される（新しい順）
3. 各日には、その日のDailyConditionが併記される
4. 行を開くと、PreWorkState / WorkContext / PerformanceResult の詳細が表示される
5. 必要ならPerformanceResultを訂正する

**表示内容（一覧行）**

```text
[日付・曜日]  睡眠 7:15  体調4  気分4  ストレス2

  09:12–10:45 (93分)  設計   認証方式の検討
    集中4 成果4 正確3 満足4  疲労 2→4 (+2)  中断1回  @自宅
  13:00–14:30 (90分)  実装   ログイン画面
    集中2 成果2 正確3 満足2  疲労 3→5 (+2)  中断4回  @オフィス
  16:00–16:08 (8分)   調査   [中断終了]
```

**正常終了**

- 一覧が表示される

**例外**

| 条件 | 挙動 |
|---|---|
| 記録が0件 | 「まだ記録がありません」と表示し、S-04への導線を出す |
| InProgressのセッションが含まれる | 「進行中」と表示する。編集させない |

**編集で許可する範囲**

| 対象 | 編集 | 理由 |
|---|---|---|
| PerformanceResult の5指標とメモ | 可 | 評価の訂正は正当。`updated_at` で事後編集を区別できる |
| WorkSession の中断回数 | 可 | 記録漏れの補正 |
| WorkSession の開始・終了時刻 | **不可** | 時刻はシステムが記録した事実。改変を許すと記録の信頼性が失われる |
| PreWorkState / WorkContext | **不可** | 結果を知った後の編集は、説明変数を汚染する（[PRD §4.1](01-product-requirements.md)） |
| DailyCondition | 当日のみ可 | 過去日の遡り編集は記憶に基づくため許可しない |
| WorkSession の削除 | **不可** | 記録は削除しない |

**PreWorkStateを編集不可にしている理由は本プロダクトの根幹である。** 「結果が悪かったから体調も悪かったことにする」という後付けを許すと、説明変数と目的変数の独立性が失われ、分析が意味を持たなくなる。

### UC-09 傾向を見る

| 項目 | 内容 |
|---|---|
| **目的** | 高いパフォーマンスが出る条件を発見する |
| **アクター** | ユーザー |
| **事前条件** | なし（データ不足時は不足と表示する） |

**操作手順**

1. S-09（分析）を開く
2. 分析期間を選ぶ（既定: 直近28日。選択肢: 7日 / 28日 / 90日 / 全期間）
3. 6種の分析結果が表示される

**表示する分析**

| ID | 分析 | 表示形式 |
|---|---|---|
| A-01 | 作業タイプ別の平均集中度 | 横棒グラフ + 件数 |
| A-02 | 作業タイプ別の平均成果度 | 横棒グラフ + 件数 |
| A-03 | 時間帯別の平均集中度 | 横棒グラフ + 件数 |
| A-04 | 曜日別の平均成果度 | 横棒グラフ + 件数 |
| A-05 | 睡眠時間区分別の平均成果度 | 横棒グラフ + 件数 |
| A-06 | 開始予定に対する実行率 | 数値 + 未実行理由の内訳 |

詳細な定義は[分析仕様書](04-analytics-spec.md)を参照。

**正常終了**

- 6種すべてが表示される
- サンプル数が5件未満の区分は「サンプル不足（n=2）」と表示し、数値・グラフを出さない

**例外**

| 条件 | 挙動 |
|---|---|
| 分析期間内にCompletedのセッションが0件 | 各分析に「データがありません」と表示 |
| すべての区分がサンプル不足 | 「まだ判断できるデータが集まっていません。あと N 件の記録が必要です」と表示 |
| A-05 で、DailyCondition未記録の日のセッションがある | それらを除外して集計し、「除外 N 件（日次コンディション未記録）」と併記する |

**表示上の制約**

- **合成スコアを表示しない。** 各指標を個別に表示する（[用語集 §6](02-glossary.md)）
- **相関係数・p値を表示しない。** MVPのサンプル数では誤った確信を与える（[PRD §7.3](01-product-requirements.md)）
- **必ず件数（n）を併記する。** 平均値だけを見せない
- **アプリ側で結論を書かない。**「午前が最も集中できています」のような断定文を出さない。数値を提示し、解釈は人間が行う

**最後の制約が重要である。** アプリが結論を出すと、ユーザーはそれを検証せず受け入れる。本プロダクトの目的は、ユーザー自身が条件を言語化すること（[PRD §9.2 S5](01-product-requirements.md)）である。

## 4. S-01（ホーム）の仕様

S-01 は「次に何を入力すべきか」を示す画面である。以下の順で表示する。

```text
┌────────────────────────────────────────┐
│ 2026年8月4日(火)                        │
├────────────────────────────────────────┤
│ ① 進行中のセッション                     │
│    ある場合のみ表示                       │
│    [タスク名] 経過 42分  → 作業中へ       │
├────────────────────────────────────────┤
│ ② 今日のコンディション                    │
│    未記録: [記録する] ボタン              │
│    記録済: 睡眠7:15 体調4 気分4 ストレス2 │
├────────────────────────────────────────┤
│ ③ 今日の予定                            │
│    予定なし: [予定を追加]                 │
│    予定あり: 各行に状態と操作             │
│      未着手 → [開始] [やらなかった]       │
│      実行済 → 完了 (93分)                │
│      未実行 → 未実行: 時間がなかった      │
│    [予定を追加]                          │
├────────────────────────────────────────┤
│ ④ 今日の記録                             │
│    完了セッション数、合計作業時間          │
├────────────────────────────────────────┤
│ ⑤ [作業を開始]（予定外の作業）            │
└────────────────────────────────────────┘
```

**状態別の制御**

| 状態 | 表示 |
|---|---|
| 進行中セッションあり | ⑤「作業を開始」を無効化する。①を最上部に強調表示 |
| 日次コンディション未記録 | ②を強調表示する |
| 未処理の予定が1件以上 かつ 現在時刻が18:00(JST)以降 | ③に「未処理の予定が N 件あります」を表示 |

## 5. S-05（作業中）の仕様

```text
┌────────────────────────────────────────┐
│ 認証方式の検討                           │
│ 設計 / 自宅                             │
│                                        │
│            00:42:15                    │
│                                        │
│ 中断: 1回   [+1]                        │
│                                        │
│ [終了]                   [中断終了]      │
└────────────────────────────────────────┘
```

**仕様**

- 経過時間は1秒ごとに更新する。計算元は `started_at`（サーバー保存値）であり、クライアントのタイマーではない。リロードしても正しい値を表示する
- 「+1」を押すと中断回数が加算される。減算はS-06で行う（誤操作の訂正）
- 中断回数はこの画面ではサーバーに送らない。S-06で確定時にまとめて送る
- ブラウザを閉じてもセッションは継続する。次回S-01 で「進行中」として復帰できる
- **一時停止機能は設けない。** 一時停止を許すと「実作業時間」の定義が曖昧になる。中断は回数でのみ記録する

## 6. 入力コンポーネントの規約

全画面で共通とする。

| 入力 | UI | 理由 |
|---|---|---|
| 1〜5の評価 | 5つのボタンを横並び。1タップで選択 | ドロップダウン・スライダーは操作が遅く、30秒制約を満たせない |
| 睡眠時間 | 時間・分の2つのセレクト（分は0/15/30/45） | 自由入力は誤入力と時間を招く |
| 作業場所 | 4つのボタン | 同上 |
| 会議件数 | 数値ステッパー（0が既定） | 大半のケースで0のまま進める |
| WorkType | ボタン列（6個以内を前提） | ドロップダウンより速い |
| TaskItem | 検索可能なリスト。直近使用順 | 件数が増えるため |

**1〜5の評価をボタンにすることは、30秒制約を満たすための必須条件である。** 作業前は3項目、作業後は5項目の評価がある。1項目5秒を超えると制約を満たせない。

## 7. MVPで実装しないUI

| 項目 | 理由 |
|---|---|
| ダークモード切替 | 観測に無関係 |
| 設定画面 | WorkTypeの管理以外に設定項目がない |
| ダッシュボードのカスタマイズ | 分析6種は固定 |

| キーボードショートカット | 記録頻度が1日数回であり、費用対効果が低い |
| オフライン対応 | 同上 |

WorkTypeの管理はS-02（タスク画面）の一部として簡易に持つ。専用の設定画面は作らない。
