## 読む順序

初めて読む場合は 1 → 2 → 4 の順で読めば、このプロダクトが何を目的とし、何を観測し、何を分析するかが分かる。

実装に入る場合は 5 → 6 → 8 → 9。

## 作成順序の制約

**分析仕様書（4）はドメイン設計書（5）より先に作成した。**

分析に必要な値から逆算してデータモデルを決めるため。この順序を守らないと「後から必要になった値が保存されていない」という事態が起きる。

例: 実行率を算出したくなっても、実行しなかった記録（NonExecutionRecord）を保存していなければ算出できない。これは遡って作れない。

[分析仕様書 §8](04-analytics-spec.md) に将来やりたい分析を列挙してあるが、必要な追加データはすべて「なし（保存済み）」になっている。これがこの順序で書いた目的である。

## 設計の要点

この4点が本プロダクトの根幹であり、実装中に失われやすい。

| # | 要点 | 出典 |
|---|---|---|
| 1 | **開始前の状態 / 作業中の事実 / 作業後の結果を分離する** — 説明変数と目的変数の独立性を保つため | [PRD §4.1](01-product-requirements.md) / [ドメイン設計 §1](05-domain-design.md) |
| 2 | **作業前状態は事後編集できない** — 結果に引きずられた後付け評価が入ると分析が無意味になる | [ドメイン設計 §4.7](05-domain-design.md) |
| 3 | **実行しなかった記録を保存する** — 実行率は遡って算出できない | [PRD §2 P4](01-product-requirements.md) |
| 4 | **記録コストの上限を守る**（開始前30秒 / 終了時60秒 / 日次30秒） — 記録が続かなければデータは貯まらない | [PRD §8 原則1](01-product-requirements.md) |

## 実装の進め方

設計書を一度に全部渡して実装させるのではなく、縦切り単位で進める。詳細は[実装タスク分解](09-implementation-tasks.md)。

```text
縦切り1  記録の中核（タスク → 作業前 → 開始 → 終了 → 評価 → 履歴）  → 実運用開始
縦切り2  日次コンディション・予定・未実行記録
縦切り3  分析6種
縦切り4  仕上げ
```

**縦切り1が完成した時点で実運用を開始する。** 分析には28日分のデータが必要であり、全実装の完了を待って記録を始めると検証が1ヶ月遅れる。

Claudeへの指示テンプレートは[実装タスク分解 §6](09-implementation-tasks.md)にある。

## 実装中の禁止事項

[技術設計書 §8](08-technical-design.md) に13項目ある。特に破られやすいのは次の3つ。

- 作業前の入力項目を増やして30秒を超える
- TaskItem に完了フラグ・期限・優先度・タグ・親子関係を追加する
- 分析結果に結論文を出す

判定基準: 実装した機能が「タスクを消化しやすくするため」のものならスコープ外。「作業の条件と結果を観測するため」のものならスコープ内（[PRD §12](01-product-requirements.md)）。
