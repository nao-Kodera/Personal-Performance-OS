# Personal Performance OS

> タスクを管理することが目的ではない。
> 自分の状態・環境・行動・成果を観測し、**高いパフォーマンスが出る条件を発見して再現する**ことが目的である。

タスク管理アプリだと思って使うと、機能が足りないと感じる。目的が違う。

| | 一般的なタスク管理アプリ | このアプリ |
|---|---|---|
| 中心にあるもの | タスク | 作業セッションと、その前後の状態 |
| 「完了」の意味 | ゴール | 観測データ1件 |
| 成功とは | タスクが消化されること | 自分の再現条件が分かること |
| 得られるもの | 進捗の可視化 | 「どういうときに調子が出るか」の答え |

そのため、**タスクに完了ボタンも期限も優先度もない。** 詳しくは[わざと付けていない機能](#わざと付けていない機能)。

---

## 記録の流れ

1日に何度か、この3ステップを回す。

```
作業を始める前          作業中              作業が終わったら
─────────────      ──────────      ──────────────
疲労・集中の見込み・      経過時間を見る       集中・成果・正確性・
気分・場所・会議件数      中断があれば +1      満足・終了時の疲労
                                          
   結果を知らない        事実だけ            結果を知ってから
   時点の「条件」                            付ける「評価」
```

**この3つを分けることが、このアプリの全てである。**

作業前の状態を「あとで」記録できてしまうと、結果が悪かった日に「あの日は疲れてたことにしよう」と後付けができてしまう。そうなると「疲れているとパフォーマンスが落ちる」という当たり前の結論しか出てこなくなり、記録した時間が無駄になる。

だから**作業前の記録は、あとから編集できない。** これは仕様であって、機能の不足ではない。

## いま使えること / まだ使えないこと

### 使える

| 画面 | パス | できること |
|---|---|---|
| ホーム | `/` | 進行中の作業、今日の記録、作業開始への導線 |
| タスク | `/tasks` | 観測の単位となるタスクの登録・編集・アーカイブ |
| 作業開始 | `/sessions/start` | 作業前の状態と環境を記録して開始 |
| 作業中 | `/sessions/active` | 経過時間の確認、中断回数のカウント |
| 成果評価 | `/sessions/:id/finish` | 5指標の評価を記録して終了 |
| 履歴 | `/history` | 過去の記録の確認と、成果評価の訂正 |

### まだ使えない

| 機能 | 予定 |
|---|---|
| 日次コンディション（睡眠・体調・気分・ストレス） | 次の開発段階 |
| 作業予定と、実行しなかった記録 | 次の開発段階 |
| 分析（作業タイプ別・時間帯別・場所別など6種） | その次 |

**分析にはデータが必要である。** 少なくとも28日分、各区分5件以上が貯まらないと結果は表示されない。だから分析機能が未完成のうちから記録を始める。

## 起動する

### 初回だけ

```bash
# 依存パッケージ
cd frontend && npm install && cd ..

# データベース（コンテナ）
docker compose up -d db

# テーブルを作る
dotnet ef database update \
  --project backend/src/PerformanceOs.Infrastructure \
  --startup-project backend/src/PerformanceOs.Infrastructure
```

**マイグレーションは自動適用されない。** アプリ起動時に勝手にスキーマが変わると、意図しないタイミングでデータ構造が変わる。明示的に実行する。

### 毎回

3つとも起動する。ターミナルを3つ使うか、バックグラウンドで動かす。

```bash
docker compose up -d db                                    # データベース
dotnet run --project backend/src/PerformanceOs.Api         # API   → localhost:5238
cd frontend && npm run dev                                 # 画面  → localhost:5173
```

ブラウザで <http://localhost:5173> を開く。

> `docker-compose.yml` には `api` と `web` のサービス定義もあるが、**Dockerfile が未作成のため今は使えない。** `docker compose up -d db` で DB だけ起動し、API と画面はローカルで動かす。

### 止める

```bash
docker compose stop db      # データは残る
```

`docker compose down -v` は**使わない。** ボリュームごと消え、記録が失われる。

## 使い方

### 1. タスクを登録する（`/tasks`）

観測の単位を作る。「認証方式の検討」「ログイン画面の実装」のように、**1回の作業で扱う粒度**にする。

- **タイトル**（必須）
- **既定の作業タイプ**（必須）— 作業開始時に自動で選ばれる。その場で変更できる
- **メモ**（任意）

同じ名前のタスクを何度登録してもよい。同じ作業を別の機会に行うのは正常なことである。

使わなくなったタスクは**アーカイブ**する。選択肢から消えるだけで、過去の記録は残る。

### 2. 作業を開始する（`/sessions/start`）

**ここが一番重要な画面である。** 目標は30秒以内。

| 入力 | 既定値 |
|---|---|
| タスク | — （検索で絞り込める。直近使った順に並ぶ） |
| 作業タイプ | タスクの既定値が自動で入る |
| 疲労度 | なし（毎回選ぶ） |
| 集中できそうか | なし（毎回選ぶ） |
| 気分 | なし（毎回選ぶ） |
| 作業場所 | なし（毎回選ぶ） |
| 今日の会議件数 | 0 |
| 割り込みが予想されるか | いいえ |

**評価3項目に既定値がないのは意図的である。** 既定値のまま進めると、観測していない値が記録されてしまう。

開始時刻は**サーバーが決める。** 手入力できない。あとから「実は9時から始めてた」と書き換えられると、作業時間の分析が事実に基づかなくなる。

> **同時に記録できる作業は1件だけ。** 並行作業を記録しても、どちらの成果か分けられないため。進行中の作業があるとき、開始ボタンは押せない。

### 3. 作業中（`/sessions/active`）

- 経過時間が1秒ごとに進む
- 中断されたら **+1** を押す（減らすのは次の画面）

**ブラウザを閉じても、PCを再起動しても、セッションは続いている。** 経過時間はサーバーが記録した開始時刻から毎回計算しているため、正しい値が表示される。次に開いたときホームに「作業中」と出る。

**一時停止はない。** 一時停止を許すと「実際に作業していた時間」の定義が曖昧になる。中断は回数だけ記録する。

作業として成立しなかったとき（すぐ会議に呼ばれた等）は **中断終了** を使う。分析の対象からは外れるが、記録としては残る。「開始したが作業にならなかった」という事実自体が情報である。

### 4. 成果を評価する（`/sessions/:id/finish`）

目標は60秒以内。**5指標すべてが必須。**

| 指標 | 何を答えるか |
|---|---|
| 集中度 | どれくらい集中できたか |
| 成果度 | どれくらい進んだか |
| 正確性 | 質はどうだったか |
| 満足度 | 納得できる時間だったか |
| 終了時疲労度 | 終わった時点でどれくらい疲れているか |

**スキップできない。** 評価が欠けた記録は分析に使えず、そこまでの記録が無駄になるため。

記録すると、**疲労がどれだけ増えたか**と、**見込んだ集中と実際の集中の差**が表示される。

### 5. 履歴を見る・訂正する（`/history`）

日付ごとに記録が並ぶ。行をクリックすると詳細が開く。

**訂正できるのは、成果評価の5指標・メモ・中断回数だけ。**

| | 訂正 | 理由 |
|---|---|---|
| 成果評価・中断回数 | できる | あとから見て評価が変わるのは正当 |
| 開始・終了時刻 | **できない** | システムが記録した事実だから |
| 作業前の状態・環境 | **できない** | 結果を知ってから直すと、分析が意味を失うから |
| 記録の削除 | **できない** | 記録された事実は消さない |

訂正した記録には「訂正」と表示される。あとから直したものかどうかが分かるようにしてある。

## 評価の尺度

すべて1〜5。**疲労度だけ「高いほど悪い」で、他は「高いほど良い」。**

数値を反転して表示することはしない。記録した値と表示される値は常に一致する。

### 疲労度・終了時疲労度（高いほど疲れている）

| 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| 疲れていない | やや疲れている | 普通 | 疲れている | 限界に近い |

### 気分（高いほど良い）

| 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| 非常に悪い | 悪い | 普通 | 良い | 非常に良い |

### 集中できそうか（作業前の見込み）

| 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| 集中できる気がしない | あまり期待できない | 普通 | 集中できそう | 非常に集中できそう |

### 集中度（作業後の実際）

| 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| ほぼ集中できなかった | 何度も気が散った | 普通 | よく集中できた | 完全に没入した |

> 「集中できそうか」と「集中度」は別の指標である。**見込みと実際の差**が、自分の予測がどれくらい当たるかを示す。成果評価の直後にこの差が表示される。

### 成果度

| 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| ほとんど進まなかった | 想定を下回った | 想定どおり | 想定を上回った | 大きく前進した |

### 正確性

| 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| 手戻りが確実に必要 | 手直しが多そう | 普通 | 質は高い | やり直しの余地がない |

### 満足度

| 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| 時間を無駄にした | 納得できない | 普通 | 納得できる | 非常に良い時間だった |

**基準を途中で変えないこと。** 「最近は基準が厳しくなった」という状態になると、時系列の比較ができなくなる。迷ったら3を選ぶ。

## わざと付けていない機能

「不足」ではなく「設計」である。追加すると、このアプリが解こうとしている問題が解けなくなる。

| ないもの | 理由 |
|---|---|
| タスクの完了ボタン | 完了はゴールではなく観測1件。使わなくなったらアーカイブする |
| 期限・優先度・タグ・サブタスク | タスクを消化しやすくする機能であって、観測とは関係がない |
| 作業前の状態の編集 | 結果を知ってから直せると、原因と結果が独立でなくなる |
| 開始・終了時刻の手入力 | 記憶に基づく後付けの記録ができてしまう |
| 成果評価のスキップ | 評価のない記録は分析に使えない |
| 記録の削除 | 記録された事実は消さない。誤りは訂正で直す |
| 一時停止 | 「実作業時間」の定義が曖昧になる |
| 総合スコア | 5指標は意味が違う。平均すると何を観測したのか分からなくなる |
| 通知・リマインダー | 記録を強制する仕組みではない |

## 記録が続かないとき

**記録が続かなければ、このアプリは失敗する。** データが貯まらなければ分析できない。

だから記録コストに上限を決めてある。

| 場面 | 目標時間 |
|---|---|
| 作業開始 | 30秒 |
| 成果評価 | 60秒 |

**この時間を超えるようなら、入力項目を増やしたのが原因である。**「この項目も記録すれば後で分析できる」という理由で項目が増えるのが、このアプリが最も壊れやすい壊れ方である。

超えている場合は、項目を足すのではなく**削る**。

## データはどこにあるか

PostgreSQL コンテナのボリューム（`pgdata`）の中にある。外部に送信されない。

バックアップを取るときは:

```bash
docker compose exec db pg_dump -U performance_os performance_os > backup.sql
```
